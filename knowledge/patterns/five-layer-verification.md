# 驗收五層梯

> 「系統的眼睛只能證明系統做到了它被告知的事。」

五種驗證方式,按「最常抓到真正的問題」排序。**前兩名是用玩家的眼睛看,後三名是用系統的眼睛看** —— 而系統的眼睛只能證明系統做到了它被告知的事。

| 層 | 抓什麼 | 誰在看 |
|---|---|---|
| 1. 使用者實玩 + run 紀錄 | 規格本身錯了 | 玩家 |
| 2. 沒有前後文的 agent 讀截圖 / 錄影 | 做了但看不見 | 玩家(代理) |
| 3. 平衡探針 | 機制沒有份量 | 系統 |
| 4. headless 測試 | 迴歸 | 系統 |
| 5. autotest 全速跑完 | 死鎖 | 系統 |

## 規則

- **每一趟 run 自動寫純文字紀錄。** 路線選擇、每層的名冊與資源、開戰時每個單位的座標、戰果與存活數、每個獎勵/事件/購買的結果。驗屍靠它。
- **在 commit 前要有人看過畫面,不是等使用者看。** 開真視窗跑 N 幀存 PNG 自動退出,再把 PNG 讀回來。差別在於**可以在 commit 前抓到**。
- **看的人要換一個。** ⚠️ **未實測** —— 蓋的人看不出「做了但看不見」,因為他知道那顆火球在那裡,所以他就看見了。把圖和這次的判準丟給一個沒有前後文的 subagent,不要告訴它你做了什麼。下面的案例是蓋的人自己看畫面抓到的,所以這條是**對那個做法的修正提案,不是它的紀錄**。
- **收尾錄一段 15–20 秒影片並看過再說做完。** ⚠️ **未實測** —— 這是 godogen 上游的做法,深坑公會沒有跑過。它被列在這裡是因為下面那個案例顯示截圖在時序問題上是盲的,不是因為錄影已經被證明有效。
- **測試綠不等於做對。** 見 [[fake-green-tests]]。
- 三、四、五層全綠而使用者仍說「沒感覺」時,回到第 2 層。見 [[presentation-before-numbers]]。

## 案例

**第 1 層:規格錯了,測試永遠測不到(深坑公會)**

使用者給了一份輸掉的 run 紀錄。從裡面讀出:六場有兩場沒帶英雄(`出征：＋3隊` 開頭沒有英雄名)、弓手×12 這隊值 24 費用 = 上限的 69%、第 8 層帶主力就帶不了盾牆,所以他把主力留在家、全滅。

**這是純數據推出來的因果鏈,而系統完全按規格運作 —— 是規格錯了。**

**第 2 層:兩個測試永遠不會紅的問題(commit `084f126`)**

高草的顏色跟草地只差一階(等於沒畫);禁佈署區的圖例有紅色但地上沒有。都是 agent 自己讀截圖抓到的。

**截圖在時序問題上是盲的:** 近戰單位在原地抖動 —— 截圖完全看不出來,最後是靠逐拍 CSV 追蹤才發現是「追擊 → 目標死 → 走回崗位 → 再追」的迴圈,20 拍走了 4.4 格、淨位移 0.7 格。

這是實際事故。「有錄影的話一眼就看到」是當事人的推測,**還沒有人驗證過** —— 逐拍 CSV 才是那次真正抓到它的工具。

**第 3 層:機制沒有份量**

四種佈陣策略全部 100% 勝、零傷亡 —— 站哪都一樣。見 [[mechanism-weight]]。

**第 5 層:死鎖**

方格佈署上線後抓到:最後一個敵人待在所有警戒圈外,而單位錨定在格子上不會去追,`L=12 R=1` 卡死。後來把「超過 9000 tick 就印出現場狀態並 `quit(2)`」變成常駐診斷。
