# 跨專案知識語料

這裡是 godogen 的長期記憶。遊戲 repo 是拋棄式的,這個目錄不是 —— 在某一個遊戲裡踩到的坑,寫進這裡才能帶到下一個。

publish 時整份複製進遊戲 repo 的 `kg-seed/`,由 kg 匯入 `craft.db`。agent 在 session 開始、context 壓縮後、以及每次送出訊息時會自動收到相關條目。

## 三個分類

| 分類 | 收什麼 | 判準 |
|---|---|---|
| `pitfalls/` | 會靜默失敗的具體技術陷阱 | 「照著寫會壞,而且不會報錯」 |
| `principles/` | 設計與決策的通則 | 「知道這條會做出不同的選擇」 |
| `patterns/` | 可重用的架構或流程 | 「下次直接照這個蓋」 |

## 檔案格式

```markdown
---
source: pitguild-2026-08
verified: true
---
# 標題

> 「一句話版本」

內文……
```

**`source`** —— 這條哪來的。從其他專案帶過來的保留原始出處,不要洗成通則;具體的來源讓讀的人能判斷它適不適用於當下。

**`verified`** —— 有沒有人真的踩過:

| 值 | 意思 |
|---|---|
| `true` | 有具體事故,內文寫得出數字、檔名或 commit |
| `partial` | 部分實測、部分是推論。**內文必須逐項標出哪些是哪些** |
| `false` | 整條都沒被驗證過 |

不是 `true` 的條目,內文要有 `⚠️ 未實測` 標記在**具體的那一項旁邊** —— frontmatter 的旗標不會被渲染給讀的人看,寫在那裡等於沒警告。

**開頭那句 `> 「一句話版本」` 不是排版,是機制。** 匯入器只在找到 `「」` 引言時把節點標成 `principle`,而壓縮後的重新注入**只注入 principle**。少了這行,這條會靜默降級成不會被注入的等級。它同時也是注入時印出來的「原話」,所以要寫成能獨立成立的一句。

它必須是全檔第一個 `「」`(匯入器取的是 `quotes[0]`,依文件順序),所以標題裡不要用引號。

## 寫作規範

**每條必須有「規則」與「案例」兩段。**

- **規則**段:條列,祈使句,講「該怎麼做」而不是「為什麼重要」。
- **案例**段:具體到可驗證 —— 數字、檔名、commit hash、seed、實際錯誤訊息。

**沒有案例的條目不收。** 沒踩過的教訓不是知識,是猜想。一條寫不出具體案例的規則,通常代表它其實是從別處抄來的通則,而通則模型本來就會。

## 收錄門檻

一條知識要進到這裡,必須同時滿足:

1. **模型推不出來。** 從程式碼、文件、或第一原理讀不出這件事。「要寫測試」不算;「`play_sound()` 查無此名是靜默 return,所以要為它寫存在性測試」算。
2. **跨專案成立。** 換一個遊戲、換一個題材仍然為真。某個遊戲的平衡數值不算;「動玩家資源曲線必須附難度回歸量測」算。
3. **踩過。** 見上。

## 案例的來源標註

從其他專案帶過來的案例保留原始出處(專案名、commit、日期),不要洗成通則。具體的來源讓讀的人能判斷它適不適用於當下。
