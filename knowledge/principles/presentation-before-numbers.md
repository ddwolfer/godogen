# 不好玩要先查呈現層,再查數值

> 「多數時候不是不夠強,是看不見——而 agent 的直覺永遠是去調數字。」

使用者說某個機制「沒感覺」時,多數情況不是它不夠強,是**看不見**。

這條對 agent 特別重要,因為 agent 的直覺反應永遠是去調數字 —— 那是它看得到的東西。呈現層的缺失在程式碼裡沒有任何痕跡。

## 規則

- 收到「X 沒感覺 / 不好玩」的回饋,**先問「玩家看得到它發生嗎」,再問「數值夠不夠」**。
- 檢查順序:有沒有視覺回饋 → 視覺回饋看得清楚嗎 → 時機對嗎 → 才輪到數值。
- 每加一個機制,同一個 commit 裡就要有它的呈現。分兩次做,中間那次就是假機制。
- 呈現層的顏色/對比要用**遊戲鏡頭**驗收,不是用色票。差一階等於沒畫。

## 案例

**統計(深坑公會)**

「使用者覺得某個機制沒感覺」的案例裡,約**三分之二**的根因在呈現層,不在數值。

**高草看不見(commit `084f126`)**

高草地形的第一版顏色跟草地只差一階 —— 機制完全正確,玩家眼裡什麼都沒發生。同一個 commit 還有:禁佈署區的圖例有紅色,但地上沒有紅色。

**兩個都不會有任何測試會紅。** 是 agent 自己讀截圖抓到的。

**武技**

數值做到完全正確,回饋是「我完全沒特別看」。
