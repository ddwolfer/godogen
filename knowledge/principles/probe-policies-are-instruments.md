# 平衡探針的代理策略是儀器,不是事實

> 「代理策略是你寫的程式,它會有 bug——而它的 bug 會偽裝成設計結論。」

平衡探針靠腳本代理跑幾百場。那些代理**是程式碼**,所以它們會壞。一個壞掉的「打得好」代理跑出來的低勝率,長得跟「這個機制沒有份量」一模一樣。

模型推不出這條,因為 `if counter <= random: print("機制沒份量")` 這行判斷在每一個層面上都合理 —— 你確實應該拿最佳解跟亂玩比。錯的是**你事先指定了誰是最佳解**。

## 規則

- **不要事先指定哪個策略代表「打得好」。** 讓探針掃過所有策略、自己挑出勝率最高的那個,並且**把它的名字印在報告裡**。
- 某個策略異常落後時,**先讀它的決策程式碼,再懷疑遊戲數值**。代理的 bug 比遊戲的 bug 便宜太多。
- 代理策略的改動與遊戲數值的改動**要分開提交、分開量測**。改儀器不是改遊戲,混在一起下一輪數據沒法歸因。見 [[one-knob-at-a-time]]。
- 策略池至少要有一個「什麼都不做」的下界。上界會壞,下界不會 —— 空板還能贏就是機制沒份量,這個結論不依賴任何代理寫得好不好。

## 案例

**「元素取捨沒有份量」是假警報(元素牌堆,2026-08-14)**

探針的判定寫死成 `counter`(照波次需求買塔)對 `random`:

```gdscript
if counter_win <= random_win:
    print("playing to the wave is no better than random - no weight yet")
```

第一次跑出來 counter 16%、random 8%,勉強過關。修了報表格式重跑之後 counter 掉到 **4%**,判定當場印出「元素選擇沒有份量」。

那句話是錯的。同一張表裡 `tier2`(存牌等雙元素塔)是 **45%** —— 元素取捨值 37 個百分點。錯的是 counter 的決策程式碼:它會把手牌買成一階塔,24 場總共只蓋出**一座**暴風雪塔。

修 counter 的邏輯(先活過開局、之後留牌等配對)之後它上升到 12%,**仍然不是最佳**。結論是把判定改成「掃出最高的那個並印出名字」,並在 README 註明目前用 `tier2` 當基準。

如果當時相信了那句判定,下一步會是去改元素池組成或塔的數值 —— 改一個根本沒壞的東西。
